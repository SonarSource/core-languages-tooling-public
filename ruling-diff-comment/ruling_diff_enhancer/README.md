# Ruling Diff Enhancer

This module adds AI-assisted triage to the ruling diff comment generated by the
single `ruling-diff-comment` entry point. See the parent README's
[AI-assisted diff review](../README.md#ai-assisted-diff-review) section for a
local preview command and credential configuration. When `DSPY_MODEL` and a
Portkey API key are set, the main script includes reviews in the diff comment.

The enhancer discovers `sonarpedia.json` under the analyzer checkout, resolves
`rules-metadata-path` relative to each configuration, and loads local rule HTML
and JSON metadata. Missing, invalid, or ambiguous metadata is an error rather
than a reason to guess a specification. Metadata paths must stay within the
analyzer repository.

## Model Connection

Requires Python 3.10+, `uv`, and an OpenAI model enabled for your Portkey key.
Reviews are always sent to OpenAI through Portkey via the OpenAI client. Export
`PORTKEY_API_KEY_OPENAI` (or the generic `PORTKEY_API_KEY`, used when the
OpenAI-specific one is unset) using your usual secret-management mechanism;
do not put tokens in arguments, source files, or comments. The HTML, JSON, and
visible code snippets, changed finding locations and messages, repository and
rule keys are sent through Portkey to OpenAI, so Portkey's and
OpenAI's logging, access controls, and retention policies apply; this may incur
charges.
Enable the enhancer only for content approved for sharing with both services.
Obtain the applicable data-sharing approval before using it with proprietary
analyzer code.

Set `DSPY_MODEL` to the OpenAI model name, such as `gpt-4.1`; an `openai/`
prefix is accepted. GPT-5 and o-series models use the required reasoning
defaults. The enhancer does not cache source snippets locally.

## Review Results

One structured OpenAI call is made per rule/repository, merging examples from
multiple projects of the same rule. It prioritizes:

- Added issues that look like **false positives**.
- Removed issues that look like **lost true positives**.
- Otherwise, **one representative example**, not a fabricated regression.

Bad-case selections are limited to three per rule.
The predictor is instructed to prefer one strongest example and select more only
for materially different failure modes or rule exceptions, not merely different
files, projects, or names. Additional rationales must explain the distinct case.
Each selection includes its original snippet, location, classification, and a
short rationale. The integrated comment displays all selected examples before
unselected source examples, including when they come from different projects.
Unknown/duplicate IDs, impossible change-kind classifications, and mixed
representative/bad-case selections are rejected.

Each rule also receives an overall summary, an opinion on the scale
`very_negative`, `negative`, `neutral`, `positive`, and confidence `low`, `medium`,
or `high`. These are subjective triage judgments, not calibrated probabilities
or proof of correctness. A change with no visible snippets must use low
confidence and selects no examples.

In combined diff comments, a linked overview table leads to one section per
rule/repository, grouping projects and their source examples. Selected rationales
appear with the original snippets rather than repeating them in a separate review.
Color indicates the opinion only; confidence is displayed as neutral text.

Only examples already present in the comment can be selected. The producer caps
snippets and can truncate whole rule sections. Missing context, source files,
unseen examples, and line moves limit what can be inferred; human review is still
required. The enhancer never retrieves additional source context or follows
instructions embedded in rule descriptions or snippets.

## Tests

```bash
cd ruling-diff-comment
uv run --frozen --extra enhancer python -m unittest -v test_enhancer test_models
```

Tests use temporary metadata repositories, mocked predictions, and mocked HTTP
requests for the actual Portkey transport.
They make no paid/external model calls. A cold-cache install of the enhancer
dependencies requires `UV_INDEX_REPOX_USERNAME` and `UV_INDEX_REPOX_PASSWORD`
for repox package downloads. These are not model credentials.
